# Suture

面向不熟悉技术细节的同事的 AI Gate 连通工具：双击打开，一次「开始检查」看这几个
客户端能不能连上公司网关（AI Gate），能连上就是绿勾；连不上才展开「可能的原因」，
每一条都用大白话讲清楚是哪儿的问题、怎么修，能安全自动修的直接给按钮，需要你提供
Key 或选模型的给输入框 / 候选列表，处理完再测。另有一个「安装 / 上手」页，帮没装过
的同事用官方命令装好缺失的客户端并配置连 AI Gate。

覆盖三个客户端：Claude Code CLI、Codex CLI、DeepSeek Harness。

## 跑起来

```bash
python3 main.py                  # 图形界面
python3 main.py --cli            # 命令行
python3 main.py --cli --no-fix   # 只检测不修改任何文件
```

图形界面会优先用系统自带的 WebView 开一个应用窗口；初始化不成功（主要是 Linux
上没装 WebKitGTK）就退回默认浏览器，界面内容一样。设置 `SUTURE_NO_BROWSER=1`
可以只起服务、不主动拉起浏览器。

## 打包

```bash
./build/build.sh                 # 在当前这台机器上打一个单文件可执行程序
```

六个平台组合需要六台对应系统/架构的机器——PyInstaller 不能跨系统交叉编译，
这是工具本身的限制。`.github/workflows/release.yml` 里是六条并行的构建流水线，
macOS 用 universal2 把两种架构合成一个文件。

## 验收测试

```bash
python3 -m unittest discover -s tests -t .
```

测试不依赖真实网关：`mock_gateway.py` 起一个假网关，可以让它表现成正常、
5xx、限流、鉴权拒绝、跑着跑着开始出错等各种情况，用来触发各条判断分支。
每个用例都用独立的临时 HOME 和项目目录，不会碰到你自己的配置。

## 代码结构

| 位置 | 职责 |
|---|---|
| `suture/profile.py` | 加载网关规则（地址、鉴权、模型路由表），预留了从网关运行时拉取的接口 |
| `suture/harness/` | 三个客户端各一个适配器，把各自的配置结构归一化成同一套字段；另负责各自的命令探测、官方安装命令、Key 落点 |
| `suture/checks.py` | 检测项。连通失败时才作为诊断器跑，把静态问题翻译成「可能的原因」清单 |
| `suture/gateway.py` | 出网请求与响应分类 |
| `suture/fixer.py` | 备份、写入 |
| `suture/selftest.py` | 让客户端用**它自己**的配置自证能否使用（只在本机没法发验证请求时才做） |
| `suture/installer.py` | 探测 Node 运行时、执行各客户端官方安装命令并回收输出 |
| `suture/engine.py` | 单客户端四态判定（连通 / 连不上 / 没配置 / 没安装）、逐条修复动作、一键配置、整体编排；命令行和界面共用 |
| `suture/server.py` | 界面用的本地接口（state/check/action/configure/recheck/install_run），只监听 127.0.0.1 并带一次性令牌 |
| `suture/ui/index.html` | 界面本身，自包含，不引任何外部资源；「检查」「安装 / 上手」两个页 |
| `gateway_profile.json` | 网关规则。网关新增模型或调整协议时改这里，不用重新分发二进制 |

设计说明见 `DESIGN.md`，验收记录见 `VERIFICATION.md`，产品侧的判断依据见产品方案文档。

## 语义（每个客户端四态）

- **已连接（绿勾）**：真实请求能连上 AI Gate。通了就只给一个绿勾，不再罗列
  任何细项——跟连通无关的边角问题不管。
- **无法连接**：才展开「可能的原因」。原因分四类：
  `自动修复`（地址少协议、多拼 /v1、模型名大小写、**Key 没放进网关要求的
  Token 请求头**等，给「修复」按钮）/ `选模型`（模型不在网关列表，给候选下拉，
  只改目标、保留清单里其它模型）/ `填 Key`（Key 缺失或补头后仍被网关拒绝，
  输入网关后台生成的 Key）/ `外部处理`（例如 Key 得回后台重新生成、Codex 项目
  要标记可信，只给说明）。处理完用主按钮再跑一次「开始检查」验证。
- **未配置**：装了客户端但没连网关，给「配置」面板（默认模型 + Key）。
- **未安装**：引导去「安装 / 上手」页装。

## 几条守住的边界

- **Key 不出本地。** 只用于向网关发请求和写回本机配置；界面、日志、接口返回里
  一律只出现掩码后的形式（前 4 位 + 后 4 位）。
- **连通优先，成功不罗列。** 判断标准只有一个：真实请求能不能通。通就过，不把
  几十项细粒度静态检查摊在成功用户面前；静态检查降级成「连不上时才跑」的诊断器。
- **决定性请求用客户端自己配的模型发。** 模型名配错了就要被如实标出来，不能拿
  探活模型（网关保证认识）去试、把坏模型名掩盖成已连通。
- **网关侧有问题时不动本地配置。** 探的是规则里那个已知正确的地址，先确认网关
  本身活着；超时、连不上、限流、5xx 直接停下。鉴权被拒不算网关侧问题——那更可能
  是本地 Key 配错了，正是要抓的场景。
- **写配置永远先备份。** 任何一次写入（修复、存 Key、一键配置）都先备份原文件，
  出问题时人工能照着备份找回，而不是被静默覆盖。
- **只改实际生效的那一层。** Codex 的项目级配置在项目不可信时整层不生效，这种
  情况下不会去写它——写了等于没改。
- **不猜。** 配置文件读不懂就如实报错，不按猜测继续。模型名只在「明显是打字错误」
  （大小写、连字符写法）时自动纠正；如果纠正后的候选本身也是路由表里另一个独立
  型号（比如 `gpt-5.6` 与 `gpt-5.6-sol`），一律不自动改，交给用户确认——那会让人在
  不知情的情况下连到另一个模型，比直接报错更糟。

## 已知限制

- **DeepSeek Harness 的 YAML 用的是自己写的受限读取器。** 标准库没有 YAML 解析器，
  而引擎要保持只依赖标准库。支持嵌套映射、列表、标量、引号、注释；遇到锚点、块标量、
  流式写法、多文档会明确报错而不是猜。写回用户层 `settings.yaml` 时不保留原有注释
  （写前有备份）。
- **协议版本头检测默认关闭。** 网关是否校验 `anthropic-version` 尚未确认，确认后把
  `gateway_profile.json` 里 `protocol_version.check_enabled` 改成 `true` 即可，不用改代码。
- **Codex 的 base_url 是否需要 `/v1` 后缀待实测。** 按 OpenAI 兼容协议的惯例应该要带，
  代码里也是这么处理的，但需要实际连一次 Codex CLI 确认。
- **AI Gate 只从 `Token` 请求头读 Key（实测），且 Codex 能否在请求里带自定义
  `Token` 头未确认。** Claude Code CLI 靠 `ANTHROPIC_CUSTOM_HEADERS` 带 Token 头；
  DeepSeek Harness 把 Token 写在路由的 `headers.Token` 里（Suture 存 Key / 自动补头
  都会写这里）。Codex 若没有自定义请求头机制，可能得走别的方式才能连这条网关。
  网关采信哪个头由 `gateway_profile.json` 的 `auth.required_header` 声明，改了它
  判定会自动跟着变，不用改代码。
- **DeepSeek Harness 还没确认可自动执行的官方安装命令 / 非交互自证方式。** 装与测
  相关能力对它是给引导而不是自动执行；确认了正确命令后补齐即可，不用改其它逻辑。
- **签名尚未接入。** macOS 不签名 + 不公证的话 Gatekeeper 会直接拦截，非技术用户打不开；
  Windows 会弹 SmartScreen 警告。证书就绪后在构建流水线里补上这两步。
